# solenoid — `src/base/base/solenoid.py`

**최신화**: 2026-09-03 (2026-09-01 GPIO 극성 정정 4·자동 재잠금 타이머 반영)

## 역할

GPIO 릴레이로 솔레노이드를 제어한다. `mission/coupling`(자동 결합) 전용
잠금장치다. 항상 활성화돼 있으며 `enabled` 파라미터가 없다(솔레노이드는
미장착 게이트 대상이 아님).

**물리 동작(2026-08-30 사용자 확인)**: 이 커플링 걸쇠는 그냥 밀어 넣으면
스프링 힘만으로 잠긴다 — 이게 **"잠금"**이고 **무통전** 상태다(전원이
끊겨도 저절로 안 풀리는 페일세이프). **"해제"**는 솔레노이드가 실제로
동작해 걸쇠를 아래로 당겨 내리는 것이고, 이때 코일이 **통전**된다.
"해제 = 무통전"이라는 일반적인 통념과는 반대다 — 예전 코드(아래 "알려진
이슈" 참고)가 한동안 이 통념대로 짜여 있었다.

## 실행

`mars_launch/robot.launch.py`, `test_drive.launch.py`에서 뜬다.

## 설정

`src/base/config/solenoid.yaml` — `gpio_pin`(기본 23), `gpiochip`(기본 4),
`active_low`(**2026-09-01 정정 4로 `false`** — 논리 동작(잠금=무통전
스프링, 해제=통전 당김)은 그대로이고, 그 논리를 GPIO23에 실어 내보내는
극성만 뒤집혔다. 지금은 GPIO LOW = 잠금(무통전), GPIO HIGH = 해제(통전).
자세한 경위는 아래 "알려진 이슈" 참고). 코드 변수명은
`release_level`(해제, 통전) / `lock_level`(잠금, 무통전)이다 — 물리
GPIO 값(HIGH/LOW)은 `active_low`에 따라 계산되므로 정정마다 바뀐다.
`release_timeout_s`(기본 5초, **2026-09-01 신규**) — `solenoid_cmd`로
해제한 뒤 이 시간 안에 잠금 명령이 다시 안 오면 자동으로 잠금(무통전)
상태로 되돌아간다. "알려진 이슈" 3번 과열의 재발을 막는 안전장치다.

## 토픽

- 구독: `solenoid_cmd` (Bool — true=잠금)
- 발행: `solenoid_status` (Bool, 1Hz)

## 동작 요약

- **시작 시 출력을 반드시 잠금(무통전, 안전) 상태로 초기화한다**
  (2026-08-30 변경 — 예전엔 "해제" 레벨로 초기화했는데, 그게 사실은
  통전 상태였다는 게 나중에 밝혀졌다. 미션이 아무 명령도 안 보내는
  동안 코일이 계속 뜨거워지는 과열 문제의 원인이었다 — 아래 "알려진
  이슈" 3번 참고).
- gpiochip open은 `[설정값, 0, 4]` 순으로 시도해 보드 차이에 대응한다.
- GPIO claim/open이 실패하면 `sys.exit(1)`로 노드 자체가 종료된다 —
  다른 base 노드들과 달리 "안전 미장착 모드"로 계속 뜨지 않는다.
- 종료 시(`shutdown`) 항상 **잠금(무통전)** 레벨로 되돌린 뒤 칩을
  닫는다(2026-08-30 변경) — 프로세스가 죽거나 전원이 꺼지는 과정에서도
  코일이 통전 상태로 남지 않게 한다.
- **자동 재잠금(2026-09-01 신규)**: 해제 명령마다 `release_timeout_s`
  (기본 5초) 일회성 타이머를 재시작한다. 그 안에 잠금 명령이 오면
  타이머를 취소하고, 안 오면 타이머가 만료되며 노드가 스스로
  `solenoid_cmd=true`를 적용한 것처럼 잠근다 — 운용자가 해제만 해두고
  잊어버려도 코일이 계속 통전된 채 방치되지 않는다.

## 알려진 이슈

**구현됨 — 실물 재검증 필요(장시간 통전 과열 재검증, 아래 3·4번).**
**2026-08-28 — 같은 날 두 번 정정했다**:

1. **오전**: `active_low: true`(당시 설정) 상태로 `robot.launch.py`를
   실행하면, 노드가 뜨자마자 "해제"로 믿고 쓰는 신호가 실제로는
   솔레노이드를 잠그는 증상이 있었다. 릴레이 통전 여부만 실측(핀
   3.3V=통전, 0V=무통전)해 "통전=잠김"으로 가정하고 `active_low`를
   `false`로 정정했다. `robot.launch.py` 재실행으로 기동 시 더 이상
   안 잠기는 것까지는 확인했다.
2. **오후**: 웹 콘솔 수동 조작을 붙이고 실제 커플링 걸쇠가 움직이는
   방향을 확인해보니, 오전의 "통전=잠김" 가정이 틀렸다는 게 드러났다
   — 이 솔레노이드는 **통전(HIGH)하면 걸쇠가 풀리고, 무통전(LOW)이면
   스프링으로 걸쇠가 잠기는 페일세이프 구조**였다(전원이 끊겨도 결합이
   저절로 안 풀리게 하려는 설계로 보인다). "릴레이가 전기적으로
   통전됐다"와 "커플링이 기계적으로 잠겼다"는 서로 다른 축인데, 오전
   정정 때 이 둘을 같다고 가정한 게 실수였다. `active_low`를 다시
   `true`로 되돌렸다. (이때는 기동 시 "해제"로 초기화하던 코드를 그대로
   뒀는데, 그 "해제"가 사실 통전 상태였다는 걸 못 알아채 3번 문제로
   이어졌다.)
3. **2026-08-29 — 장시간 통전으로 과열 발견**(다른 세션
   `agent/follow-yaw-control-20260829`에서 발견, 이 브랜치로 반영):
   `web_manual.launch.py`를 오래 띄워둔 채(수동 CAN/모터 시험 중)
   방치했더니 사용자가 솔레노이드가 "엄청 뜨거워진" 것을 발견했다.
   코드/설계상 "해제"(커플링 안 잠긴 평상시 상태)가 곧 **통전 유지
   상태**라, 커플링을 실제로 안 쓰는 대부분의 시간에도 코일에 계속
   전류가 흐르는 구조다 — 노드가 오래 떠 있을수록 과열이 구조적으로
   누적된다. 게다가 `shutdown()`이 항상 "해제(통전)" 레벨로 복귀한 뒤
   종료하므로, **노드가 죽어도(크래시·프로세스 종료) GPIO가 마지막에
   쓰인 통전 레벨 그대로 남아 계속 열을 낼 수 있다.** **임시 조치**:
   `solenoid` 노드를 다시 띄우고 `solenoid_cmd=true`(잠금=무통전)를
   명시적으로 발행해 코일을 식혔다(이 상태를 유지하려면 노드가 계속
   떠 있어야 한다). **2026-08-30 근본 원인 수정**: 사용자가 물리 동작을
   다시 설명해줘서(위 "역할" 참고) 시작·종료 기본값이 "해제"(사실은
   통전)로 잘못 짜여 있던 게 과열의 직접 원인임이 명확해졌다.
   `solenoid.py`의 시작 시 GPIO claim과 `shutdown()`을 모두 `lock_level`
   (무통전)로 바꾸고, 변수명도 `off_level`/`on_level`(통전 방향과
   반대로 읽히기 쉬움)에서 `release_level`/`lock_level`로 바꿨다 — 실제
   GPIO 값(active_low 기반 계산식)은 그대로다. **아직 실물로 확인 못한
   것**: (1) 이제 idle 상태에서 코일이 실제로 안 뜨거워지는지, (2)
   `coupling.py`가 `align` 시작 시 명시적으로 `solenoid_cmd=false`(해제)를
   보내는 로직과 새 기본값이 잘 맞물려 자동 결합이 여전히 정상 동작하는지
   — 이 두 가지는 로봇을 다시 켜서 확인해야 한다. 이 솔레노이드가 연속
   통전 듀티를 원래 버틸 수 있는 부품인지(사양 확인)는 여전히 미확인이지만,
   평상시 기본값이 무통전으로 바뀌었으니 실사용 중 연속 통전 시간 자체가
   크게 줄어 급한 위험은 낮아졌다.
4. **2026-09-01 — 극성 재정정(정정 4) + 자동 재잠금 타이머 추가**:
   실물에서 웹 콘솔 UI가 표시하는 잠금/해제 상태와 실제 커플링 걸쇠
   동작이 반대로 확인됐다. 논리 동작 자체(잠금=무통전 스프링,
   해제=통전 당김)는 정정 2·3에서 정리한 그대로 맞지만, 그 논리를
   GPIO23 물리 레벨로 바꾸는 `active_low` 값이 틀려 있었던 것으로 보고
   `true`→`false`로 되돌렸다 — 지금은 GPIO LOW가 잠금(무통전), GPIO
   HIGH가 해제(통전)다. 이 반전은 정정 3에서 "근본 원인 수정"이라고
   확인했던 검증(과열 재발 여부, `coupling.py` 자동 결합 정상 동작
   여부)이 실제로는 반대 극성으로 이뤄졌을 수 있다는 뜻이라, 두 가지
   모두 이번 극성으로 다시 실물 확인해야 한다. 같은 커밋에서 해제
   상태로 방치되는 것을 막는 `release_timeout_s`(기본 5초) 자동
   재잠금 타이머도 추가했다(위 "설정"·"동작 요약" 참고) — 극성이 다시
   틀리더라도 무통전 방향으로 자동 복귀하므로 과열 위험을 추가로
   낮춘다.
